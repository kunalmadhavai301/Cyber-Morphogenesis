1. Post-Quantum Cryptography (PQC)

Classical public-key cryptography—predominantly RSA, Diffie-Hellman, and Elliptic Curve Cryptography (ECDH, ECDSA)—relies on mathematical problems such as integer factorization and the discrete logarithm problem over finite fields or elliptic curve groups. In 1994, Peter Shor demonstrated that a sufficiently capable quantum computer running Shor's algorithm solves these problems in polynomial time ($\mathcal{O}((\log N)^2)$), rendering all current asymmetric standards vulnerable.

Post-Quantum Cryptography encompasses cryptographic algorithms designed to run on conventional classical hardware (laptops, servers, microcontrollers) that remain secure against cryptanalysis by both classical computers and quantum computers.

2. ML-KEM Mechanics & Key Encapsulation Workflow

A Key-Encapsulation Mechanism (KEM) is a public-key cryptographic scheme specifically engineered to establish a shared symmetric secret key between two communication endpoints. Unlike classical Diffie-Hellman, ML-KEM does not require both parties to send public keys simultaneously. Instead, the protocol proceeds through three distinct phases:

Algorithm Execution Steps (NIST FIPS 203)
  1. Key Generation ($\text{KeyGen}$): The recipient (Alice) generates an encapsulation key $ek$ (public) and a matching decapsulation key $dk$ (private). $ek$ is published or transmitted over an insecure channel.
  2. Encapsulation ($\text{Encaps}$): The sender (Bob) takes $ek$ and a random seed $m$ to deterministically derive a 32-byte shared secret $K$ and an encapsulation ciphertext $c$. Bob transmits $c$ to Alice while retaining $K$.
  3. Decapsulation ($\text{Decaps}$): Alice computes $K' = \text{Decaps}(dk, c)$. If $c$ was legitimate, $K' = K$, establishing mutual key agreement.

3. Standardized Parameter Sets (NIST FIPS 203)

NIST FIPS 203 specifies three parameter sets with increasing lattice matrix dimensions $k$:

ML-KEM-768 $k=3$ Category 3 AES-192 1,184 Bytes 1,088 Bytes 32 Bytes
ML-KEM-1024 $k=4$ Category 5 AES-256 1,568 Bytes 1,568 Bytes 32 Bytes

Recommendation: NIST recommends ML-KEM-768 as the primary default parameter set for general-purpose applications, balancing robust Category 3 post-quantum security with minimal latency.

4. Implicit Rejection (FIPS 203 §5.3)

In traditional public-key encryption schemes, decapsulation errors (such as invalid padding or ciphertext modification) often raise observable error signals. Attackers can exploit differences in execution time or error codes to mount chosen-ciphertext timing attacks (e.g., Bleichenbacher padding oracle attacks).

To counter this threat, ML-KEM adopts implicit rejection. When presented with an invalid ciphertext $c$ of the expected byte length, $\text{Decaps}(dk, c)$ does not abort. Instead, it deterministically generates a pseudorandom shared secret $K' = \text{J}(z \mathbin{\Vert} c)$, where $z$ is a 32-byte rejection seed stored securely inside $dk$. An attacker receives no observable indicator of failure, neutralizing oracle side-channels.

5. Scientific Benchmarking Methodology

  • High-Resolution Monotonic Timing: Timings are captured using Python's time.perf_counter_ns(), backed by the Windows QueryPerformanceCounter() API providing 100 ns resolution.
  • Warm-up Iterations: Configurable warm-up runs (default 20 iterations) ensure CPU branch predictor, L1/L2 data cache, and runtime memory pools stabilize before timing observations begin.
  • Dual-Layer Memory Profiling: Process memory is evaluated using tracemalloc (for Python-managed heap allocations) alongside OS-level process Resident Set Size (RSS via psutil) to account for native C/Rust library execution.
  • Descriptive and Inferential Statistics: We compute sample size, mean, median, min, max, sample standard deviation ($ddof=1$), 95th percentile, Interquartile Range (IQR), and 95% Confidence Intervals of the mean.

6. Security Requirements & Academic Disclaimer

This application enforces a strict zero-secret-leakage policy:

  • Private key material is held in ephemeral RAM only and is never serialized or returned across REST endpoints.
  • Shared secrets are verified in server memory using constant-time comparisons (hmac.compare_digest).
  • Demonstrations display non-revealing SHA-256 fingerprints rather than raw secret bytes.

Academic Disclaimer: This platform is designed for research, academic evaluation, and cryptographic performance benchmarking. While using standards-compliant implementations of FIPS 203, it is not a certified production Key Management System (KMS) or Hardware Security Module (HSM).
